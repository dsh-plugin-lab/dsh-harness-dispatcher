# test/ — 规则层

继承根规则，见 [../AGENTS.md](../AGENTS.md)。本文件只写「往这里加测试要遵守什么」；
覆盖范围与运行方式见 [README.md](README.md)。

## 红线优先于覆盖率

本仓的测试不是「覆盖率工具」，是**判据**。加测试时先问：**这条断言在什么情况下会红？**
答不出来就不是测试，是装饰。

- **每条红线必须能反向控制。** 故意把对应实现改坏 → 跑到红 → 复原。
  「现在这条绿」和「这条判据有牙齿」是两件事，后者要单独证。
- 反向控制做过一次就够，但**改红线时要重做**：断言写松了、正则匹配到别的行，
  都会让它永远绿。

## 红线文件的结构

[redlines.test.ts](redlines.test.ts) 一个 `describe` 一组，编号连续（B1…B14）。
新加一条：

1. 挑下一个空号，`describe('B<n> — <一句话判据>', …)`。
2. **注释写清「哪个真实现象让这条必须存在」**——不写理由的红线下次会被当成障碍删掉。
3. 加完立刻反向控制一次。
4. 更新根 [AGENTS.md](../AGENTS.md) 的仪表盘数字（组数 + 条数）。

## 两个必须小心的坑

- **扫源码时去掉注释再断言。** 红线 B13 用 `stripComments`，否则一句注释里的旧词就误报。
- **扫文档时要连模板字符串一起看，所以用 `stripProse` 而不是 `stripComments`。**
  B4 曾经因为用了后者而漏掉了 README 模板里的 `credential` 一词。

## 不连宿主、不联网、不花额度

单测**只跑纯函数**。需要真宿主的那类验证（装进 profile、拉起子 agent）不属于这里，
是人工步骤，见 [../docs/ARCHITECTURE.md](../docs/ARCHITECTURE.md) 的「真机验证」节。

**推论**：任何只能在真机上发现的缺陷，单测都抓不到 —— 所以发现一次就在红线里补一条。
2026-11-11 的 `file:` URL 与「不挂副本」两条都是这么来的。

## 命名与位置

- 一个源文件测试对应一个 `<name>.test.ts`，与 `src/<name>.ts` 同名。
- `redlines.test.ts` 是唯一的例外：它横切所有文件，因为**判据不按文件组织**。
- 不 mock 宿主服务：需要宿主的地方就是纯函数边界没找对，先拆。
