## 1. 触发这次讨论的那个判断：我做窄了

起点是四条指导思想：**SUT / 配置即代码 / Agentic 调度 / 旁路观测**。
我把"配置即代码"实现成了一个 6 字段的枚举：

```
tools（7 选 N）· persona（5 选 1）· faults · provider/model · maxDepth
```

**用户的反应是对的：这不是"什么都能改"。** 真正被排除在外的包括——任意宿主插件行、skills、
AGENTS.md 注入、runtime context、压缩阈值、权限预设、hooks、MCP。

而当初收窄的理由是「怕模型自由生成嵌套 JSON 写错、且错得静默」。**这个理由站不住**，见 §2.3。

## 2. 四个被推翻的设想

### 2.1 「harness 是一个参数对象」→ 它的实物是一份插件行列表

`PresetDefinition.plugins` 就是行列表，`agentPresets.register()` 会**真的挂一棵 Loader 树**，
每行插件的 `apply(ctx, config)` 往**那个 agent 的 scope** 上注册工具 / prompt 段 / 服务 / 中间件。

**推论：能表达什么 = 插件能做什么 = 几乎无限。** 枚举只是这份列表的一个子集，被我错当成了它的定义。

### 2.2 「故障注入装在 preset 里」→ 它装在 Scoped 工具管线上

已落地并真机验证，不重述。**这里只留一句为什么当初想错了**：
preset 行只能改「开始时会有什么」，表达不了**时变**故障；而且行序写反会让**整份组合挂不上**。
三条 Scoped 管线（`pre-execute` / `execute` / `post-execute`）都带 `exec.agent`，一条全局监听就能按
session 精确命中——**这是"旁路"该有的形状，不是"组合"该有的形状**。

### 2.3 「收窄词汇能防错」→ 站不住

- 枚举防住的只有**拼写错误**。
- 而**行列表写错是会响的**：`mountPreset` 逐行审计，import 失败 / 激活失败 / 服务等不到，
  **当场抛，带行号**。
- 真正静默的失败是另一类：**看起来有效的空结果**（注入了一个不存在工具的故障、跑了一组其实没施加任何条件的 trial）。
- 治它的应该是**指纹 + 校验护栏**，不是收窄词汇。收窄的代价是"你真正想测的东西根本进不来"。

**证据就在本轮**：我给 `faults[].tool` 加校验后，**我自己写的测试**把 `fs`（目录键）当成了工具名。
说明问题不是"模型会写错"，而是**两套命名本身就容易混**。

### 2.4 「task 就是一条 prompt」→ task 有四个部件

| 部件 | 为什么要紧 | 现状 |
|---|---|---|
| 首条输入 | 可以不只是文本（图 / 文件 / 多段） | 只有纯文本 |
| **初始环境** | 同一句 prompt，"目录里有没有那个文件/有没有 git 仓库"是**不同的题** | 只能传 `cwd` |
| 终止条件 | 跑几轮？等它自己说完成？超时？ | 跑一轮就结束 |
| 判定信号 | 外部怎么判对错 | 不判（刻意），但也不留可判定信号 |

用户原话：「task 不一定 prompt 就是一样的」——**这条我一开始漏了**。

## 3. 讨论里最有用的一个转向：超大参数 → 文件 + 零成本校验

用户提出：行列表是个超大参数，手写不可能一次写对，**是不是要写成一个文件传进去**。

**这个方向对，而且宿主本来就是这么干的**：agent preset 就是一份 YAML 行列表文件。

由此得到的核心结论是一条**成本性质**，不是设计偏好：

| 闸 | 手段 | 代价 |
|---|---|---|
| 结构 | 宿主自带 `entryListProblem()` | 0 |
| **挂载** | 宿主自带 `mountPreset()` + `auditRows()`，逐行报诊断 | **0（不启动 agent、不花 token）** |
| 兼容 | `prepareProfileEntries()`：profile 禁掉的行会被标出 | 0 |

**"挂载一棵插件树不需要跑模型"** ——所以"写错→知道→改"的循环是零成本的，一两秒一轮。
于是「不可能一次写对」不是问题：**不要求一次写对，要求改一次就知道对不对。**

配套的两个具体动作（**尚未实现**）：
- `run_benchmark({ harness_file: '<path>' })` —— 参数从巨大对象变成一个路径
- `dump <presetId>` —— 用 `agentPresets.readDocument()` 导出出厂预设，**从能跑的东西上做减法**

还有一条：`fingerprint`（已实现）从文件内容算，回答「两次跑的是不是同一份装配」。
**这是"自由行"的判据**——内容自由了，就必须有别的机制证明两次一样。

## 4. skill 指针会变成死指针（本轮新发现）

打算写一个薄 skill，指向随包发的官方 skill：`cordis-composition-reference`（Loader 行方言 + 插件包清单）、
`editing-cordis-compositions`（怎么写/怎么验一份 preset）。

**但那些官方 skill 不是自动可见的。** 它们之所以出现在目录里，是因为 **`cordis` 预设**给
`skill-filesystem` 配了：

```yaml
customSkillDirs:
  - !!js ...resolve('@deepseek-ai/dsh-agent-preset/package.json')..., 'skills'
```

| 预设 | 配了 `customSkillDirs`？ | 官方 composition skill |
|---|---|---|
| `cordis`（本机 `selectedDefault`） | 是 | **可见** |
| `standard` | **否** | **不可见** |

**所以只写指针 = 在 `standard` 下指向不存在的东西，且不报错。**
结论：**指针 + 文件系统路径兜底**，两条都写。

两个连带结论：
- 本仓自己的 skill 应该**代码注册**（`ctx.skills.register()`，兄弟仓 `dsh-plugin-debugging` 的做法），
  **不依赖谁去改 `customSkillDirs`**；`ctx.skills` 按可选注入处理。
- 这件事本身就是 skill 的第一条内容：**"换个预设，agent 就不知道怎么写 harness 了"**。

## 5. 硬边界：什么真的不能当变量

「什么都能改」需要一条准确的上界，否则是空话。

- **能**：凡是"一个插件能做的事"，都能按 agent 单独改（工具 / 提示 / 服务 / 中间件 / 策略 / skills / 压缩）。
- **不能**：**Host 服务这一层** —— agent loop 本身、持久化、模型适配器、审批策略。
  它们一改就是改整个进程，不是改一个 agent。
- **中间地带（未验证）**：`timeout-policy`（工具调用超时）、`repeat-tool-reminder`、
  `spill-policy`（输出溢出）现在都是 Host 行。**理论上可以提进 preset 当变量**，
  但可能因服务泄漏被判 `Preset services require isolate realms` 而挂不上。**没试过，别当结论。**

另有一条已知的**不是变量、但决定外部有效性**的事实：子 agent 的审批被宿主钉成 `never`
（见 [docs/ARCHITECTURE.md §1.2](../../docs/ARCHITECTURE.md)）。

## 6. 还没拍板的四件事

每条都写清"卡在哪"，别写"待定"。

| # | 问题 | 卡在哪 | 我的倾向 |
|---|---|---|---|
| 1 | harness 文件允许 `!!js` 吗 | 允许 = 最大灵活，但 YAML 里的 `!!js` 是**任意代码执行**（宿主 preset 文档明说它不是沙箱）；禁止 = 纯数据，可用别的语言生成与比对 | **先禁止**；遇到"必须按平台自适应"再放开 |
| 2 | harness 文件放哪 | 放仓里 → 可版本化可 diff 可复现，但改一次要提交一次；放输出目录 → 随手试，但几周后不知道当时跑的是什么 | **放仓里**（`harness/*.yml`） |
| 3 | task 要不要对象化 | 对象化更真，但会连带改记录 schema、改 `task_id` 的语义（标签 vs 主键） | 先只做「输入 + 初始环境 + 终止条件」，判定信号留给外部 |
| 4 | 要不要 `llm-replay` 方向 | 录制一次模型输出 → 同一份评测零成本确定性重放 N 次；但它改变的是「模型是不是变量」这条前提 | 想试，但它应该是**另一类实验**，不能和"换装配"混在一个 run 里 |

## 7. 一条方法论教训（这条最该被记住）

**"抽象复杂"往往是命名造成的，不是本质造成的。**

用户连着几轮说"很乱""很抽象"。事后看，乱源不是 dsh 的机制，而是我用 `harness` 这个词装了两样东西：

| 词 | 实际指 |
|---|---|
| `harness`（我代码里的对象） | 我自作主张挑的 6 个快捷字段 |
| harness（用户的意思） | 那份插件行列表，全量 |

**改法不是解释得更清楚，而是让这个词回到它本来指的东西**，然后给快捷方式起**另一个名字**
（例如 `preset`/`quick`），而不是让快捷方式借用主词。

同族的第二个教训：**判据要能区分"我改了什么"**。`fingerprint` 之所以必须存在，不是因为"有用"，
而是因为**内容自由之后，"两次一样"这件事必须有机器可判的证据**，否则实验无法比较。
